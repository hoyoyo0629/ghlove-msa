# 기능 재검증 (2차) — 기부(donation) 서비스

검증일: 2026-09-08
기준 문서: `docs/requirements.md`(RFP SFR-003), `docs/isp-detailed-design-summary.md`(ISP 바운디드 컨텍스트 #2 기부관리)
대상 커밋: `f567f7c 기능 상세 구현 1차`
선행 문서: `docs/feature-verification-2026-09-08-member.md`

검증 방식은 member와 동일하다. Postgres/Kafka + member(8081)·donation(8082)·point(8083)를 실제 기동하고,
신규 회원으로 **실제 기부를 신청·완료·취소**하면서 DB와 Kafka 연계 결과까지 확인했다.

## 0. 결과 요약

| 구분 | 건수 |
|---|---|
| 🔴 심각 (법정 요건 위반·기능 불능·데이터 무결성) | 5 |

**가장 중요한 결과 두 가지를 먼저 적는다.**

  point 서비스가 구독해 기부금의 30%를 적립하는 흐름을 실호출로 확인했다(10만원 기부 → 30,000점).

## 1. 🔴 심각 결함

### 1-1. 거주지 판정 오류 — **본인 주민등록지 지자체에 기부가 된다**

`DonationService.residenceLocgovOf()`가 회원 주소에서 거주 지자체를 찾을 때, 시/도를 무시하고
**시군구명이 주소에 포함되기만 하면 매칭**한다.

```java
return normalized.startsWith(upper + name) || normalized.contains(name);
//                                            ^^^^^^^^^^^^^^^^^^^^^^^^ 시/도를 무시하는 폴백
```

주소가 `"서울시 중구 세종대로"`인 회원으로 검증한 결과:

```
POST /api/donate/verify-residence {"locgovCode":"11140"}   (서울 중구 = 본인 거주지)
  -> {"psitnLocgovCode":"31110","userRegion":"울산광역시 중구"}   ← 거주지를 울산 중구로 오판

POST /api/donate {"locgovCode":"11140","amount":100000}
  -> {"cntrSn":"D202609081140466132"}                      ← 본인 주민등록지에 기부 성공 (법 위반)

POST /api/donate {"locgovCode":"31110","amount":100000}
  -> {"message":"자신의 주민등록주소지의 지자체에는 기부를 하실 수 없습니다."}  ← 무관한 지자체를 오차단
```

원인은 두 겹이다.
1. DB의 시도명은 `"서울특별시"`인데 회원 주소는 `"서울시"`로 시작해서 `startsWith(upper+name)` 정밀 매칭이 실패한다.
2. 그러면 `contains("중구")` 폴백이 걸리는데, "중구"는 서울·부산·대구·대전·울산에 모두 존재한다.
   이후 `max(시군구명 길이)`로 고르므로 동률(전부 2글자)에서는 **목록상 먼저 나온 울산 중구**가 선택된다.

**영향**: 일반기부(`createGeneralDonation`)와 지정기부(`createDesignatedDonation`) **양쪽 모두** 이 함수를
쓰므로 둘 다 영향을 받는다. "중구/남구/북구/동구/서구"처럼 여러 시도에 같은 이름이 있는 자치구
거주자 전원이 이 버그의 대상이다.

**조치**: 주소 → 지자체 매핑을 문자열 `contains` 추정이 아니라 **행정표준코드(법정동/도로명주소 API) 기반**으로
바꾸거나, 최소한 회원 가입 시 지자체 코드를 직접 선택·저장해야 한다. 폴백 `contains(name)`은
시/도가 확정되지 않은 상태에서는 절대 단독으로 쓰면 안 된다.

### 1-2. 연간 기부한도 우회 — 2,000만원 한도에 **5,980만원 기부 완료**

한도 검증(`validateAnnualLimit`)은 **기부 "신청" 시점에만**, 그것도 **이미 COMPLETED된 건만 합산**해서 판정한다.
`completeDonation()`에는 한도 재검증이 **전혀 없다.**

```
1) 19,900,000원 기부 신청 3건 연속 생성 -> 3건 모두 성공
   (신청 상태는 누적에 포함되지 않으므로 매번 "올해 누적 0원"으로 통과)
2) 3건 모두 완료 처리 -> 3건 모두 {"status":"OK"}

올해 누적 기부액(COMPLETED): 59,800,000원   ← 한도 20,000,000원
적립된 포인트:              17,940,000점
```

RFP SFR-003의 "연간 기부한도 및 지자체별 세부 규칙 검증" 요건이 실질적으로 무력화된다.
포인트는 기부액의 30%이므로 **한도 우회는 곧 재정 손실**로 직결된다.

**조치**: `completeDonation()`에서 한도를 재검증하거나, 한도 합산 대상에 REQUESTED(결제대기) 건을
포함시켜 신청 단계에서 선점되도록 해야 한다. 후자가 이중 신청 방지 측면에서 더 안전하다.

### 1-3. 기부금 운용현황 조회가 **완전 불능**(500) — 엔티티 타입 불일치

`GET /api/ctbny-opratn`이 **항상 500**이다. 기존 데이터 4건이 이미 들어 있는데 한 건도 읽지 못한다.

```
DB   donation.g_ctbny_opratn.expndtr_de   character varying(8)   -- 값 예: "20260210"
JPA  CtbnyOpratn.expndtrDe                LocalDateTime          -- ← 불일치

ERROR: Bad value for type timestamp/date/time: 20260210
       Could not extract column [6] from JDBC ResultSet
```

RFP SFR-003의 "지자체별 기부금 운용 현황 조회"에 해당하는 기능이 조회·등록·수정 전부 사용 불가다.
(같은 엔티티를 쓰는 등록/수정 경로도 varchar(8) 컬럼에 timestamp를 쓰려 하므로 동일하게 실패한다.)

**조치**: `expndtrDe`를 `String`으로 변경(다른 날짜 필드들이 이미 yyyyMMdd 문자열 관례를 따르고 있다).

### 1-4. 포인트 잔액이 **음수**가 된다 — 사용한 포인트까지 회수

기부 취소 시 적립 포인트를 회수하는데, **이미 사용한 포인트인지 확인하지 않는다.**

```
포인트 잔액 11,970,000점
-> 11,900,000점 사용 (잔액 70,000점)
-> 기부 취소(5,970,000점 적립분) 실행
-> 잔액: -5,900,000점    ← 음수
```

ISP는 포인트관리 설계 원칙을 "포인트를 **화폐성 자원**으로 간주해 거래 무결성과 감사 추적 가능성을 확보"로
명시한다(원본 p.367). 음수 잔액은 이 원칙에 정면으로 위배되며, 이후 정산·통계 금액이 전부 오염된다.

책임은 두 서비스에 걸쳐 있다 — donation은 납부완료 건의 무조건 취소를 허용하고, point는 잔액 검사 없이
차감한다. point 서비스 검증에서 다시 다룬다.

**조치**: 기부 취소 전 가용 포인트 확인(부족 시 취소 거부 또는 환불 절차로 분기) + point 원장에
음수 방지 제약. 근본적으로는 §2-2의 "환불" 상태 도입과 함께 설계돼야 한다.

### 1-5. 관리자·내부 API 전면 무인증 (member와 동일 패턴)

donation에도 관리자 API 인증 인터셉터가 없다. 인증 없이 호출해 성공한 것들:

```
GET  /api/admin/donations/all        -> 전체 기부 원장(회원ID·금액·지자체) 전량
GET  /api/admin/donation-levy        -> 세외수입 부과번호·수납일자 전량
GET  /api/admin/relay-log            -> 외부연계 로그 전량
GET  /api/locgov-admin               -> 지자체 관리 정보 (등록/수정/삭제 POST도 무인증)
GET  /api/designated-projects/admin  -> 지정기부사업 관리 (생성/수정도 무인증)
GET  /api/cntr-reqmng                -> 기탁서 목록 (loginId·userName 등 개인정보 포함)
GET  /api/offgive                    -> 오프라인 기부 접수 내역
GET  /api/my-summary?userId=1000     -> {"totalAmt":6665000,...}  임의 회원의 기부 총액 조회
```

특히 기탁서 승인 API는 **승인자 ID를 클라이언트가 지정**한다.

```java
@PostMapping("/api/cntr-reqmng/{reqId}/approve")
public ResponseEntity<?> approve(@PathVariable Long reqId, @RequestParam Long managerId)
```

인증 없이 `?managerId=99999` 같은 임의 값으로 호출 가능하므로 **승인 이력 자체를 위조**할 수 있다.
(단 해당 건은 "기부금 사용이력이 존재해 승인을 할 수 없습니다"라는 비즈니스 가드에 막혀 실제 승인은
되지 않았다 — 가드는 정상 동작한다.)

ISP의 N2SF 보안설계상 결제정보·기부금액·회원정보는 전부 **S등급(민감)** 이다.

## 2. 🟠 중간 결함

### 2-1. 결제수단(계좌이체/카드결제/간편결제)이 구현되지 않음

RFP SFR-003은 "기부금 납부 및 세외수입 연계: … **계좌이체/카드결제/간편결제**"를 명시한다.
그러나 donation 코드 전체에 **결제수단이라는 개념 자체가 없다**(`payMethod`류 필드·코드 전무).

현재 `completeDonation()`은 사용자가 결제수단을 고르는 단계 없이 곧바로 세외수입 부과(`registerLevy`)와
수납확인(`confirmPayment`)을 호출한다. 즉 "결제"가 아니라 "완료 버튼"이다.

세외수입 연계 클라이언트(위택스 `wetax.go.kr`, 서울 `etax.seoul.go.kr`) 자체는 존재하고
`enabled=false` 목업 상태인데, 이건 방화벽 미개통 상 타당하다. 문제는 **그 앞단의 결제수단 선택 UX와
데이터 모델이 아예 없다**는 점이다.

### 2-2. 기부 상태가 3종뿐 — "결제대기"·"환불" 없음, 납부완료 건을 사용자가 임의 취소

```java
STATUS_REQUESTED / STATUS_COMPLETED / STATUS_CANCELLED   // 이게 전부
```

RFP는 "기부 상태관리(신청/**결제대기**/납부완료/취소/**환불** 등)"를 요구한다. 현재는 신청과 결제대기가
구분되지 않고, **환불 상태가 없어 취소와 환불이 뭉뚱그려져 있다.**

실제로 **납부완료(COMPLETED)된 기부를 회원이 마이페이지에서 그냥 취소**할 수 있음을 확인했다
(`POST /api/my/donations/{cntrSn}/cancel` → 즉시 CANCELLED). 세외수입으로 이미 수납된 돈인데
지자체 승인 절차 없이 회원 단독으로 취소된다. §1-4의 음수 포인트도 여기서 파생된다.

### 2-3. 상태코드·세액공제율 하드코딩 (RFP "하드코딩 금지" 원칙 위반)

RFP 구현 원칙은 "코드성 데이터(**상태코드**/카테고리코드/**설정값** 등)는 Java enum·상수로 박아넣지 않고
무조건 DB 테이블에서 조회"다. 현재 상태는 일관성이 없다.

| 항목 | 관리 방식 | 판정 |
|---|---|---|
| 연간 기부한도 | 공통코드 `SYSTEM_CONFIG/ANNUAL_TOTAL_LIMIT` 조회 | ✅ 원칙 준수 |
| 지자체별 한도 | `g_ctbny_setup.lmt_amt` 조회 | ✅ 원칙 준수 |
| 포인트 적립률 | point 서비스 `pt_locgov_point_rate` 조회 | ✅ 원칙 준수 |
| 기부 상태코드 | Java `static final String` | ❌ 위반 |
| 세액공제 세율 | Java `static final BigDecimal` | ❌ 위반 |

세액공제는 3구간 상수로 박혀 있다.

```java
TIER1(10만원 이하)      = 1.0    (100%)
TIER2(10만~20만원)      = 0.44   (44%)
TIER3(20만원 초과)      = 0.165  (16.5%)   / 재해지역 0.33
```

계산 자체는 코드대로 정확하다(2,000만원 → 3,411,000원 = 100,000×1 + 100,000×0.44 + 19,800,000×0.165).
다만 **세액공제율은 법 개정 시 바뀌는 대표적인 설정값**이므로 DB로 옮겨야 한다. 아울러 TIER2 구간
44%는 근거가 코드에 남아 있지 않으니, 현행 「조세특례제한법」상 고향사랑기부금 공제율과 담당 부서
확인이 필요하다(2,000만원 한도는 이미 개정분이 반영되어 있다).

### 2-4. 기부확인증의 지자체 사업자등록번호(`bizRno`)가 비어 있음

```
GET /api/my/receipts/certificate -> rows[0].bizRno = null
```

기부확인증·영수증의 발행기관 표기 항목이므로 지자체 마스터에 값을 채우거나 발급 시 검증이 필요하다.

부가로 확인된 정상 항목:
- 세외수입(위택스/서울ETAX) 및 국세청 전자영수증 연계 클라이언트가 **서울/전국 분기까지 구현**되어 있고
