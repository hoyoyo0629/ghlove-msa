## Ⅰ. 사업개요 — 핵심 요약 (p.1–17)

사업배경/추진범위/방법론 등 관리적 내용은 스킵. 다만 **"2. 컨설팅 결과 요약"(p.5–17)** 은 전체 산출물의 압축 요약이라 아래만 발췌.

- **최종 판정**: 고향사랑e음은 클라우드 네이티브 전환 대상이며, **SaaS 도입 대상 0건**, **PaaS 전환 대상 = 응용시스템(WEB, WAS)**, **IaaS 전환 대상 = 검색서버·DB(Cubrid) 등 솔루션 기반 시스템**. 전개모델은 **Single Cloud**(민간 퍼블릭 클라우드, 대구센터 PPP). 기관 자체 분류상 중요도 등급은 **"中"**. (원본 p.9)
- **목표 마이크로서비스 아키텍처**: 6개 마이크로서비스 — **회원관리 / 기부관리 / 포인트관리 / 운영관리 / 주문관리 / 답례품관리** — 각각 독립 DB를 가지며, API Gateway를 통해 대민웹/관리자(운영)웹/답례품제공자(운영)웹 3개 프론트엔드가 접근. 서비스 간에는 Message Broker(비동기 메시징)로 연계. 외부연계시스템(디지털예산, 도로명주소, 카카오, 서울시ETAX, 인터넷망, 통계청SNS, 위택스, 실명인증(SGI솔루션), 네이버, 전자정부표준프레임워크, 전자지방자치인감, 서울시세우편) 및 내부연계시스템(행정망, 공동이용시스템, 세무시스템, 디지털서비스개방포털, 국세청, 마이행정, 서울시세우편)이 API Gateway 바깥쪽에서 붙는 구조. (원본 p.11)
  - ⚠ **우리 구현과 비교**: 우리는 6개 서비스를 **member/donation/point/gift/order/admin**으로 명명했다 — ISP 문서의 "회원/기부/포인트/답례품/주문/운영"과 1:1 대응(운영관리=admin, 답례품관리=gift, 주문관리=order). 이름은 다르지만 **6개 도메인 분할 자체는 정확히 일치**한다.
- **인프라(IaaS) 목표구성**: 대구센터 PPP(Public-Private Partnership) 클라우드 환경. DMZ-VPC(WAF×2, vIPS×2) → Prod-VPC(운영 K8s 클러스터: Master Node Pool 1~3, Worker Node Pool 1~n, Kafka 백킹, 로그/모니터링 아웃터 아키텍처) / Dev-VPC(개발 K8s 클러스터, 동일 구성) / Prod-VPC-DB(기부DB, 회원DB, 답례품DB, 주문DB 등 도메인별 DB 각각 이중화) / MGMT-VPC(모니터링·공통관리서버, CI/CD: ArgoCD/GitLab/SonarQube/Nexus/Jenkins, Vault/Keycloak/Polaris/Harbor). (원본 p.15)
  - ⚠ **미반영 추정**: 우리 로컬/구현 환경은 단일 개발 스택 위주로 대구PPP 이중화·Dev/Prod VPC 분리·Velero 백업 등 실제 클라우드 인프라 배포는 아직 없음(이 프로젝트 특성상 당연히 후순위이나, 실제 이관 시 참고 필요).
- **이행과제 4개** (2026년 8개월 로드맵, M1~M8):
  1. **클라우드 네이티브 환경구축**(설계→전환구축→안정화, SaaS/PaaS/IaaS 구성, 외부아키텍처(API GW/CI-CD/Telemetry/Backing Service) 구성 포함)
  2. **고향사랑e음 데이터 정비 및 이관**(통합DB 구조를 마이크로서비스별 데이터로 분리·독립성 확보)
  3. **고향사랑e음 MSA 전환**(모놀리식→도메인 기반 MSA로 분리, 탄력적 변경·배포 체계)
  4. **클라우드 네이티브 운영·DevSecOps 체계 구축**(CI/CD 자동화, 개발-운영-보안 통합 관리)
  (원본 p.17)
- **비용/편익**: 2027–2032년 총편익 165.5억원, 총비용(2025 투자비+2027-2032 운영비) 108.4억원, NPV 57.1억원, B/C비율 1.53. (원본 p.19, 참고용 수치라 개발과 무관)

## Ⅱ. 현황분석 — 핵심 요약 (p.18–192)

AS-IS 상세 업무/화면/DB 분석은 실제 AS-IS 소스코드를 이미 보유하고 있으므로 스킵. 여기서는 **ISP 문서에서만 확인 가능한 인터뷰 결과·시사점(Key Findings)·개선기회**만 정리.

### 목차 구조 (원본 p.19, Ⅱ장 내부 TOC)
1. 현황분석 개요 / 2. 업무 현황분석 / 3. 정보기술(IT) 현황분석(3.1개요, 3.2시스템일반현황, 3.3응용현황분석, 3.4데이터현황분석, 3.5기술현황분석, 3.6연계현황분석, 3.7백업현황분석) / 4. IT거버넌스 현황분석 / 5. 요구사항 분석(킥오프 인터뷰) / 6. 현황분석 종합(6.1시사점종합, 6.2개선기회도출)

### 3.3 응용 현황분석 — AS-IS 기능 인벤토리 (원본 p.61–121 부근)
AS-IS 시스템 기능을 "대기능(사용자/관리자/답례품제공자)"별로 표 형태로 전수 나열(단위기능 수백 개, 화면ID까지). 사용자 기능은 **회원가입/로그인/기부안내/기부하기/마이페이지/고객센터** 6개 대기능, 관리자·판매자(Seller) 측은 화면ID(`UI_M0301xxxx`, `UI_S0101xxx` 형식)까지 딸린 접근권한 매트릭스(시스템담당자/지자체담당자(주·부)/답례품제공자/오프라인담당자 등)로 정리되어 있음. (원본 p.61, p.78, p.90)
- ⚠ 이 전수 기능목록은 우리가 이미 실제 AS-IS 소스코드 기반으로 화면 단위까지 이행을 완료한 상태이므로 재확인용으로만 가치 있음. 접근권한 매트릭스(시스템담당자(주/부)/지자체담당자(주/부)/답례품제공자/오프라인담당자(주/부))는 우리 admin RBAC 6단계(ROLE_ADMIN_1~6) 설계와 세부 축이 다를 수 있어 필요시 대조할 가치 있음.

### 3.4 데이터 현황분석 — DB 주제영역 (원본 p.121)
AS-IS DB(CUBRID 단일 DB)를 상품정보(OP) 등 **100개 이상 엔티티**로 구성된 대규모 모놀리식 구조로 분석. 주제영역: remittance(정산), send(메일전송로그), role/session/shadow(권한·세션), seller(판매자), sequence(채번), restock(재고알림), claim(클레임), brand, faq, wishlist, island(도서산간), featured(기획전), category, visit(접속), data(게시판), common(공통코드), display(화면전시), community, allow(IP관리), batch. Key Findings: "100개 이상 엔티티로 결합도가 높아 유지보수 어려움", "업무 영역 구분은 명확하나 순수 기부제 시스템을 넘어 쇼핑몰형 구조로 확장된 특징". (원본 p.121)

### 3.5 기술 현황분석 — SW 현황 (원본 p.133)
AS-IS 시스템SW 구성: OS는 **EOS 제품**(RHEL 계열, 상위버전 업그레이드 필요), WEB/WAS/DBMS는 공개SW 각 5/5/4종 + 상용SW 기타 99종. Key Finding: "WEB/WAS/DBMS의 공개SW는 클라우드 전환 시 동일 SW 업그레이드 방향으로 구축", "기타 상용SW는 상세조사 후 목표모델 아키텍처 설계 시 클라우드 재활용 대상 확정 필요". (원본 p.133)

### 4.2 IT거버넌스 — 운영조직 (원본 p.145)
AS-IS 운영조직: 행정안전부/균형발전진흥과 → 전 지방자치단체(위탁기관) / 한국지역정보개발원(수탁기관) → 디지털재정본부 → **지역상생정보부(4명)** 산하 **고향사랑e음 운영지원단(총 22명)**: 사업관리(3명)/운영개발(9명)/상담센터(5명)/비상주지원(5명). 별도 지역클라우드센터가 서비스장애처리/SW장애처리/Infra H/W장애 담당. (원본 p.145)

### 4.3 운영 프로세스 — 장애처리 (원본 p.157)
장애발생 → 장애접수및내용분석 → 1차단순조치(Yes/No) → (No시) 장애유형판단→자체해결/협력업체사업자판단조치 → 2차전문가조치 → 장애조치및결과보고(전화/FAX/E-mail) → 장애관리(조치결과이력관리). Key Finding: "IT 운영조직의 전문성 확보 및 지원 필요, 유지보수 업체와 유기적 협업 중요", "진행과정이 구두/문서로 진행돼 단계가 존재하며 효율적 업무체계 정립 필요". (원본 p.157)

### 5.2 인터뷰 결과 — 킥오프 인터뷰 (원본 p.175)
- 인터뷰 주제: "MSA기반 클라우드 네이티브 전환을 위한 현황파악 및 요구사항 수집" (2024.08.12, KLID 소통2회의실). 참석: KLID 디지털재정본부 지역상생정보부 원장·신승엽 책임, 정보사회진흥원, 고향사랑e음 유지관리 이상기 상무 외 6명.
- **주요 요청사항/과제** (원문 그대로 보존할 가치 있음):
  - 데이터·연계·보안: 주민등록·세외수입 등 실시간 연계 중이므로 민간 클라우드 전환 시 연계 보장 여부 검토 필요. 연계 시스템 18개, 일부 실시간/일별 배치 방식.
  - **결론 및 요청 과제**: ① 연말 트래픽 부하 해소(DB 부하 분산 구조 설계), ② 지자체 비용 부담 최소화 설계, ③ 데이터 구조·보안 고려한 클라우드 전환.
  - Key Finding: "고향사랑e음 서비스는 행정망 통해 실시간 연계 업무가 중요하며 민간클라우드 전환시 원활한 연계 수행에 대한 보장이 필수", "연말 기부에 따른 서비스 트래픽 부하 분산, 지자체 비용 절감, 연계서비스의 안정적 유지가 반드시 선행될 전환구축 필요". (원본 p.175)
  - ⚠ **연계 시스템 18개**라는 구체적 숫자가 여기서만 확인됨 — 우리 `external_integrations_architecture` 메모의 연계 클라이언트 목록과 개수 대조해볼 가치 있음.

### 6.1 시사점 종합 — 업무 현황 (원본 p.183)
- Key Findings: 고향사랑기부금 제도는 행안부 정책총괄→KLID 플랫폼운영→지자체 현장집행→금융기관 결제지원→국민 참여의 **다층적 협력구조**(중앙-지방-민간)로 운영. 「고향사랑 기부금에 관한 법률」제12조(제도 홍보·연구) 및 제8조(세액공제 관련) 등 근거 법령이 정보시스템 보안 리스크와 직결(기부자정보/주소·성명/결제정보/세액공제 데이터가 동일 시스템에서 동시 처리). 제8조(한도 30%) 등 비즈니스 규칙이 강하게 적용됨(기부한도, 주민등록지 제외, 답례품 제공한도 30%).
- **MSA 시사점**(문서 원문):
  - "서비스 경계를 명확히 하고 책임을 분리하여 조직 구조와 서비스 아키텍처를 정렬 필요 (예: 기부금 접수/정산, 세액공제 처리, 결제 서비스, 지자체 관리 등은 독립 서비스로 분리)"

  - "도메인 서비스 분리와 독립배포: 기부관리, 결제, 세액공제, 답례품, 배송, 알림, 회원/인증 등 Bounded Context별 마이크로서비스 설계 필요, 서비스 간 결합도가 낮은 경계를 찾을 필요"

## Ⅲ. 목표모델 수립 (p.193–589) — ★핵심 챕터

전체 691페이지 중 397페이지(58%)를 차지하는 문서의 핵심부. MSA 논리설계(이벤트스토밍→바운디드컨텍스트→마이크로서비스), 인프라/클라우드 상세설계, 네트워크·보안, 용량설계, 데이터 구조설계, IT거버넌스를 모두 포함한다.

### Ⅲ.1 목표모델 수립 개요 & MSA 적합성 판정 (p.193–204, p.229–252 일부)

- **MSA 도입 적합성 검토**: 4개 분야 13개 체크리스트(①안정적 서비스운영 4개, ②업무·기술변화대응 5개, ③개발품질향상 2개, ④개발생산성향상 2개)로 평가. 그중 문항 1-2·1-3("특정 시점에 10만명 이상의 대국민 서비스 접속 요청이 발생하는 시스템인가")에 해당하면 **다른 항목과 무관하게 무조건 MSA 도입**으로 판정되는 규칙. 고향사랑e음은 이 문항에 해당되어 **"클라우드 네이티브 도입 적합"** 최종 판정을 받음(연말 기부 집중 트래픽이 근거). (원본 p.257, p.261)
- **클라우드 기본설계 종합 결과**: SaaS 도입 대상 0건(CSAP 인증 152종 SaaS 상품 중 고향사랑e음 기능요건 충족하는 서비스 부재), **PaaS = 응용시스템(WEB, WAS)**, **IaaS = 검색서버·DB(Cubrid) 등 솔루션 기반 시스템**, **MSA = 고향사랑e음 응용 아키텍처 전체**, 전개모델 Single Cloud. (Ⅰ장 요약과 동일 내용, 원본 p.253)

### Ⅲ.2~3 정보화 비전·전략수립 / 추진과제 상세화 (p.205–228)

- **전략 1〉클라우드 네이티브 환경 적용을 통한 안정성 확보**: 그 세부 실행안 중 하나로 **CDN 서비스 도입**을 설계함 — 답례품 소개 이미지 등 정적 콘텐츠를 원본서버(웹서버/Object Storage)에서 CDN Edge Server로 캐싱 전송, HTTPS 프로토콜로 원본-엣지 간 통신 보안, TTL 만료 시 자동 콘텐츠 삭제. 기대효과: 응답속도 개선(다수 사용자 동시접속 시 엣지서버 분산 처리), DDoS 방어(글로벌 CDN망 보안기능), 비용 관리(대용량 트래픽에도 안정적 서비스, 정액 요금제). (원본 p.213)
  - ⚠ **미반영**: CDN은 로컬 개발 단계에서는 당연히 미도입. 실제 클라우드 이관 시 답례품 이미지 서빙 경로에 CDN을 앞단에 두는 설계를 참고할 것.
- **전략 3〉지자체·민간의 기능개선 요구 충족을 위한 민첩한 대응 환경 마련**: "도메인 중심의 MSA 설계로 도메인별 독립 배포와 확장(Scale-out)이 가능한 구조로 전환되어 장애 격리 및 성능 유연성이 향상되며, 공통 API를 통해 백엔드 서비스를 재사용함으로써 개발 효율성과 유지보수성이 개선"이라는 원칙을 재확인. 목표 서비스 구성도는 대민웹/업무웹/답례품제공자웹 3개 프론트엔드 → API Gateway → 회원관리/기부관리/주문관리/포인트관리/답례품관리(Scale-out 강조)/운영관리 6개 도메인. (원본 p.217)
- **추진과제 4개**는 Ⅰ장 요약과 동일(클라우드 네이티브 환경구축/데이터 정비 및 이관/MSA 전환/운영·DevSecOps 체계구축).

### Ⅲ.5.3 IaaS 상세설계 기준 — 인프라 전환 규칙 (p.265–348)

- **스토리지**: OS·SW 등 시스템 디스크는 블록 스토리지, 비정형 데이터는 CSP Kubernetes Service, 파일 공유/문서관리는 기타 PaaS로 분리. 블록 스토리지 적용 우선 검토가 원칙. (원본 p.265)
- **WEB/WAS 전환 유형**: 상용 SW는 동일 상용 SW로 전환(라이선스 재활용, 예: IIS→IIS), 국산·공개 SW도 동일 유지, 다만 WebtoB/Webtier iPlanet 같은 특수목적 상용은 국산·공개 SW로 대체 검토. 원칙: **WAS Migration은 상용SW는 라이선스 재활용 우선, 재활용 불가 시 국산·공개SW로 플랫폼 변경(최신버전 적용), 공개SW는 EOS 대상이 아니면 그대로 전환**(단 Wildfly→Tomcat처럼 예외 있음). (원본 p.277, p.349)
- **DB Migration**: **CUBRID → PostgreSQL**(이기종 DB 마이그레이션, 자동화 도구 사용 + 데이터 마이그레이션). Tibero/MySQL/MariaDB/MSSQL/PostgreSQL 등 기존에 이미 있던 DBMS는 동일 유지(전환 대상 아님, EOL 아닌 경우 그대로 전환). (원본 p.289, p.349)
  - ⚠ **우리 구현과 완전 일치**: 우리는 이미 CUBRID(및 원 소스)를 **PostgreSQL**로 전환해 6개 서비스 스키마를 구성했다(`as_is_schema_import_550_tables` 메모). ISP 설계와 정확히 일치.
- **인프라 상세설계(H/W)**: 대구센터 PPP 목표 구성 — 내부연계서버#1/#2(8Core/64GB/100GB, 이중화 VM), 개발내부연계(4Core/8GB), 모니터링/공통관리(4Core/8GB), 서버/DB접근제어(4Core/16GB), 백신/패치관리(4Core/8GB). PPP 전환 시 모니터링/공통관리서버, 서버/DB접근제어, 백신/패치관리 3종은 **행정망에 별도 구성** 필요(공동 인프라이므로). (원본 p.301, p.499)
- **SW 목록**: 개발 K8s Worker Node POD별 SW 인벤토리를 상세 정의 — 예: 기부관리 POD는 WAS(Apache Tomcat 11 공개), DBMS문서보안(Fasoo Enterprise DRM 5, 상용), 개인정보접속기록(WEDDS BlackBox Suite 2, 상용), AP모니터링(제니퍼 5, 상용) 재활용. 회원관리 POD는 추가로 PKI공인인증(MagicLine 4, 상용) 포함. (원본 p.325)
  - ⚠ 상용 SW 다수(Fasoo DRM 문서보안, WEDDS BlackBox 개인정보접속기록, 제니퍼 AP모니터링, MagicLine PKI인증)가 **"재활용" 전제로 설계**되어 있음 — 우리 프로젝트는 이 상용 라이선스 연동을 전부 목업(enabled=false)으로 처리한 상태(`external_integrations_architecture` 메모). 실제 이관 시엔 이 상용 SW들이 실제로 붙는다는 전제.

### Ⅲ.5.4.4 MSA 논리설계 — 이벤트스토밍 → 바운디드 컨텍스트 → 마이크로서비스 (p.349–469) ★가장 중요

**방법론**: 도메인 주도 설계(DDD) 워크숍 기반, 이벤트스토밍 기법으로 Bounded Context 식별. 순서: 도메인 이벤트 도출 → Command 도출 → Aggregate 도출 → Policy 도출 → ReadModel 도출 → External System 도출 → Bounded Context 식별. 사용자 스토리(User Story, `As a / I want to / So that` + Acceptance Criteria 형식)도 함께 작성됨 — 예: "기부금 납부(이택스)"(서울시 및 산하 자치단체 기부자가 이택스로 납부), "오프라인 기부(농협)"(인증수단 없는 사용자가 농협 방문 기부). (원본 p.361, p.385, p.391, p.397)

**애그리거트 할당 예시(회원/인증 도메인)**: `MemberRegistered`(회원가입완료)→Member 애그리거트(불변식: 동일 주민번호 중복 불가), `IdentityVerified/IdentityVerificationFailed`→Auth 애그리거트, `LoginSucceeded/LoginFailed`→Auth 애그리거트(정상 계정만 로그인 성공). 제공자계정(ProviderAccount)도 별도 애그리거트로 `ProviderAccountCreated`/`InitialLoginSucceeded`/`PasswordChanged` 이벤트 보유. (원본 p.403)

**비즈니스 기능분해 → 마이크로서비스 후보 매핑**: 8개 응용기능(기부관리/답례품관리/배치및로그/외부연계관리/운영및공통관리/정산관리/주문및배송관리/포인트관리/회원및인증관리)을 응집·결합도 기준으로 3개 서브도메인으로 그룹화:
- **Core(핵심) 서브도메인**: 기부관리, 답례품관리
- **Supporting(지원) 서브도메인**: 포인트관리, 운영관리, 주문관리(주문·배송·클레임 통합)
- **Generic(일반) 서브도메인**: 회원관리

→ 최종 **6개 마이크로서비스 후보**(기부관리/답례품관리/포인트관리/회원관리/운영관리/주문관리)로 도출되며, "이벤트스토밍으로 도출한 마이크로서비스와 일치"함을 명시(즉 이벤트스토밍과 기능분해 두 방법론이 교차검증됨). (원본 p.415, p.427)

- ⚠ **우리 구현과 비교**: 우리 6개 서비스(member/donation/point/gift/order/admin)는 이 표와 도메인 경계가 정확히 일치한다. 다만 **정산(Settlement)/세금계산서 발급 기능이 ISP 문서에서는 "운영관리" 서비스 책임으로 설계**되어 있는데, 우리 프로젝트에서 정산(Settlement)은 `offgive_and_remittance_rounds` 메모에 따르면 이미 있는 기능의 gap-fill로 처리했고 admin 서비스 쪽 소관인지 재확인 가치 있음. 반품/교환/클레임은 order 서비스(우리도 동일), 알림 발송은 우리 프로젝트에 별도 알림 서비스가 없고 이메일 등으로 처리 중인 것으로 보임(`OpEmailService` 등) — ISP의 "알림게이트웨이"라는 별도 인터페이스 개념은 미반영.

**AS-IS→TO-BE 아키텍처 매핑**: AS-IS는 프론트엔드 3종(대민Web/답례품제공자(업무)Web/관리자(업무)Web) + 백엔드가 기부(사용자/관리/연계), 답례품(관리/연계/사용자), 1차 답례품시스템(연계) 등으로 뒤섞인 모놀리식 구조. TO-BE는 프론트엔드 3종은 그대로 유지하고 백엔드만 6개 도메인별 마이크로서비스(N:N 매핑)로 재편. 아키텍처 특징: **API Gateway + 이벤트 기반 비동기통신**, 서비스 독립성 확보·장애격리·신속 배포·확장성 향상. (원본 p.439)

**CQRS 패턴 적용**: Command(쓰기)와 Query(읽기)를 물리적으로 분리하는 모델 채택. 답례품관리 적용 사례 — Command 범위: 답례품 등록/수정/승인/노출/승인/재고관리 등 실시간 관리가 필요한 쓰기(엄격); Query(조회) 범위: 카테고리별/검색/필터/정렬 등 조회 성능 최적화가 필요한 읽기(빠름). 연계서비스 예시: 주문관리는 주문 시 답례품 정보/재고 확인, 운영관리는 답례품 통계·관리자 대시보드. 핵심 포인트: "쓰기(Command)는 정합성 중심 관리, 읽기(Query)는 조회 최적화 구조 유지, 이벤트(Event)로 두 세계를 느슨하게 연결". (원본 p.433)

**마이크로서비스별 엔티티 명세(대표 사례 — 운영관리, 답례품관리, 포인트관리)**:
- **답례품관리 MSA**: 프론트(대민Web/업무관리Web/운영관리Web) → REST API(`/api/sc/*`) → 답례품관리 MSA → 답례품 DB(R/W). 주요 엔티티: `op_item`(답례품기본정보: 상품ID/판매자ID/상품코드/고객사상품코드/상품명/상품데이터형태/공개여부/판매가), `op_item_option`(옵션: 옵션ID/추가금액/재고연동여부/재고수량), `op_seller`(제공자정보: 제공자ID/제공자명(업체명)/사업자등록번호/대표자명/연락처/이메일/정산계좌정보/상태코드/계약시작일/종료일), `rwd_item_view`(답례품조회 ReadModel — 조회전용 Search Index 계층 분리). (원본 p.253/445)
- **운영관리 MSA**: 프론트 3종 → REST API(`/api/sc/*`) → 운영관리 MSA → 운영관리 DB. 주요 엔티티: `op_common_code`(공통코드), `op_config`(시스템설정), `op_settlement`(정산헤더: 정산ID/정산기간/지자체코드/제공자ID/정산상태코드/정산총액/정산생성일시/정산마감일시), `op_settlement_item`(정산상세: 상세ID/상품ID/공급가/수수료/장려금/포인트사용액/조정금액 — **비고에 "SAGA 보상(정산 취소)" 명시**), `ops_stat_*`(통계/리포트 테이블군: 기간별/지자체별/기부금액/포인트적립현황/제공자별실적/채널별실적), `op_menu/op_role/op_acl`(메뉴/권한: 메뉴ID/URL/상위메뉴ID/정렬순서/롤/사용자·그룹-롤매핑/권한유형 — 비고에 "운영자/담당자 계정(별도 Admin User 또는 회원마스터)" 명시). (원본 p.259/373/379)
  - ⚠ **정산이 SAGA 보상 트랜잭션으로 명시적으로 설계**되어 있음 — 우리 프로젝트가 이미 order 서비스에서 Kafka 초레오그래피 SAGA를 쓰고 있으므로(`saga_choreography_vs_orchestration`), 정산 취소도 동일 패턴으로 보상 이벤트를 발행하는지 점검할 가치 있음.
- **포인트관리 MSA**: 단위기능 = 포인트 적립/차감/예약/예약해제/잔액조회/거래내역조회. "포인트를 화폐성 자원으로 간주해 거래 무결성과 감사 추적 가능성을 확보하며, 이후 주문/정산의 기준 금액을 제공"이 설계 원칙. (원본 p.367)
  - ⚠ 우리 point 서비스의 예약(reservation)/확정/해제 기능은 이미 `vue3_storefront_migration_round15_point_reservations` 라운드에서 구현 완료 — ISP 설계와 일치.

### Ⅲ.5.4.5 외부 아키텍처 — API Gateway·백킹서비스·계정통합관리 (p.457–481)

검토된 솔루션 후보와 선정 논리:
- **API Gateway**: KONG Ingress Controller & API Gateway(2021 Gartner MQ 리더, NGINX+Cassandra+Lua 기반, Lua Script 커스텀 플러그인) / NGINX Plus Ingress Controller / Spring Cloud Gateway 3종을 비교 검토. (원본 p.457)
  - ⚠ **우리 구현과 일치**: 우리는 이미 **Kong**을 API Gateway로 채택했다(`sfr010_gateway_openapi_round` 메모) — ISP가 검토한 3개 후보 중 정확히 Kong을 선택한 것과 부합.
- **컨테이너 관리**: Kubernetes(오케스트레이션 사실상 표준) 채택, Namespace를 프론트엔드(fe)/백엔드(be)/운영관리(bff, op) 3개 그룹으로 분리 관리. 네임스페이스 명명규칙: 업무시스템은 `gohyang-fe`/`gohyang-be`, 운영관리는 그룹별 고정 네임스페이스 `op-log`(로그관리)/`op-trace`(추적관리)/`op-monitor`(모니터링)/`op-gitops`(GitOps)/`op-cicd`(빌드관리/개발환경)/`op-common`(점검·백업, 공통서비스). 개발환경(Dev)은 운영(Ops)과 동일 네임스페이스 정의 사용. (원본 p.355, p.463)
- **백킹서비스(검색/분석)**: OpenSearch(상용 Elasticsearch 대안, fluentd로 로그 수집→OpenSearch 저장·검색·시각화, Kibana 격의 Open Dashboard) 채택. (원본 p.469)
- **계정 통합관리**: Keycloak(오픈소스 IAM, OIDC 기반) 채택 — 기관 전반 계정·권한·정책을 단일 플랫폼에서 통합 관리, AD/LDAP 등 기존 인증체계와 연동 가능. (원본 p.481)
  - ⚠ **미반영 추정**: 우리는 Keycloak을 도입하지 않고 서비스별 자체 인증(JWT)을 구현한 것으로 보임(`admin_console_auth`, `admin_rbac_6tier_role_round` 등 메모에 자체 RBAC 구현 언급, Keycloak 언급 없음). 이는 로컬 개발 단계 특성상 합리적 생략이나, 실제 클라우드 이관 시 중앙 IAM 도입이 설계상 전제되어 있음을 기억할 것.

**서비스별 정확한 K8s 프로젝트/네임스페이스명**(컨테이너 상세설계 용량산정표에서 확인, 원본 p.511):
`gohyang-fe-www`(대민(기부자)WEB), `gohyang-fe-work`(업무WEB), `gohyang-fe-operation`(운영관리WEB) / `gohyang-be-member`(회원관리), `gohyang-be-donation`(기부관리), `gohyang-be-point`(포인트관리), `gohyang-be-returnPresent`(답례품관리), `gohyang-be-order`(주문관리), `gohyang-be-operation`(운영관리). WorkNode 사양 16Core/64GB×5대, 서비스별 CPU/Mem Request·Limit 및 오토스케일링 Min/Max(대부분 2~4, 답례품관리 등 트래픽 민감 서비스는 최대 10)까지 설계됨.
  - ⚠ 서비스명 대응: ISP의 `returnPresent`(답례품관리) = 우리 `gift`, ISP의 `operation`(운영관리) = 우리 `admin`. 나머지 4개(member/donation/point/order)는 이름까지 동일.

### Ⅲ.5.4.6 용량설계 (p.481–528)

- **Tier 구조 전환 원칙**: AS-IS는 1-Tier 또는 Web/WAS 미분리 2-Tier가 혼재 → TO-BE는 **3-Tier(Web-WAS-DB) 표준화**(Web/WAS 분리 불가 시 2-Tier로 예외 허용). Zone 구성: Web은 DMZ(Public Zone), WAS·DB는 Private Zone. 플랫폼 전환 규칙: U2L(Unix→Linux), L2L(Linux→Linux), W2W(Windows 유지). (원본 p.487)
- **용량 산정 기준**: VM 타입은 SV0202(2Core/2GB)~SV64256(64Core/256GB) 표준 규격 사용. 산정 계수 — 적정 Core 비율 0.8, CPU 여유사용률 1.3, **MSA 가중치 1.4**(MSA 전환에 따른 추가 오버헤드 반영), 운영환경 MSA Outer Architecture(모니터링/로그/트레이싱 등 사이드카·공통 인프라)에 CPU 24코어/메모리 96GB, 개발환경엔 CPU 40코어/메모리 160GB 별도 배정. (원본 p.515)
- **신규 생성 서버(공통인프라)**: 개발외부연계(리포팅), 개발내부연계(배치), 모니터링/공통관리서버, DB암호화(PrivacyDB 적용), 서버/DB접근제어(CSP 접근제어 권장 사양), 백신/패치관리(CSP상품 규격 최소 권장) — 각 4Core/8~16GB. (원본 p.499)
- **컨테이너(운영환경) 용량**: 서비스별 Request/Limit CPU·메모리와 오토스케일링 범위를 프론트/백엔드 각 6개씩 세밀 설계(위 네임스페이스 표 참조). (원본 p.511)

### Ⅲ.5.4.7 데이터 구조 설계 (p.505–528)

- **설계 원칙 — Database Per Service**: 각 마이크로서비스의 데이터베이스를 비공개로 유지하고 API를 통해서만 접근하도록 설계(마이크로서비스 간 데이터 레이어 공유 금지). 장점: 서비스 간 변경 영향 차단, 서비스별 최적 DB 유형 선택 가능(예: 텍스트검색은 ElasticSearch, 소셜그래프는 Neo4j 식으로 이질적 DB 채택 가능). 단점: 분산 트랜잭션 구현 복잡(SAGA 패턴으로 대응 권장), 여러 DB에 걸친 조회 어려움(CQRS 패턴으로 대응 권장). (원본 p.517)
- **DB 물리적 분리 방식**: "**DBMS는 이중화 구성하고, 각 시스템의 마이크로서비스별 DB는 스키마를 분리**하여 전환 리스크와 비용을 최소화" — 완전히 별도의 DB 인스턴스가 아니라 이중화된 DBMS 인스턴스 위에 서비스별 스키마를 분리하는 절충 방식. (원본 p.523)
  - ✅ **우리 구현과 정확히 일치**: `feedback_ghlove_core_shared_db_schema` 메모에 따르면 member/donation/point/admin/order는 `ghlove_core`라는 공유 DB의 별도 스키마를 쓰고 있다(gift만 별도 DB) — 이것이 바로 ISP가 제시한 "DBMS 이중화 공유 + 논리 스키마 분리" 방식과 정확히 일치하는 설계다. 우연이든 의도든 ISP 설계 의도와 부합하는 좋은 사례.
- **AS-IS→TO-BE DB 분리 매핑**: AS-IS는 "고향사랑e음DB"(클레임/운영/기부(포인트)/외부연계/주문/답례품/배송 스키마가 한 DB에 혼재) + "통계DB"(통계) 2개 물리 DB → TO-BE는 **회원관리DB/기부관리DB/포인트관리DB/운영관리DB/주문관리DB/답례품관리DB 6개**로 분리. 매핑이 단순 1:1이 아니라 교차 매핑(예: AS-IS "기부(포인트)" 스키마가 TO-BE 기부관리DB와 포인트관리DB 양쪽으로 갈라짐, AS-IS "배송"이 TO-BE 주문관리DB로 흡수)됨에 유의. (원본 p.521)

### Ⅲ.6 기술 및 보안 구조 설계 (p.529–540)

- **네트워크 아키텍처(민간클라우드 적용 기준)**: 인터넷 사용자 → F/W → vIPS → WAF → VPC-Prod(DMZ Subnet에 로드밸런서+운영 API G/W, Prod AP Private Subnet에 Kubernetes Cluster(운영) — Frontend/Backend/Operation 3개 Namespace, Prod DB Private Subnet에 고향사랑 MSA 운영 DB군) / VPC-Prod와 별도로 Dev AP Public/Private Subnet(개발 API G/W, Kubernetes Cluster(개발), 개발 DB) 구성 / VPC-MGMT(클라우드 공통관리, Peering GW로 타 VPC와 연결) / 지역정보개발원과는 IPSec VPN으로 연결. 외부연계 API 호출은 클라우드 인터넷망 경유, 내부연계 API 호출은 IPSecVPN을 통해 기관망 또는 메타넷 Indigo 보안 활용. (원본 p.529)
  - ⚠ **미반영**: 로컬 개발 환경엔 VPC 분리·WAF·vIPS·IPSec VPN 등 실제 네트워크 보안계층이 당연히 없음. 실제 클라우드 이관 설계 시 참고.
- **보안 아키텍처 — N2SF(국가 망 보안체계) 준용**: 데이터를 공개(O)/S등급(민감) 2단계로 분류 — **회원정보(이름/연락처/주소), 결제정보(기부금액/결제수단/트랜잭션내역), 관리자계정정보, 시스템로그는 전부 S등급**, 지역별 기부현황/통계/답례품목록만 공개(O)등급. 통제영역별 설계: ① 망구조(VPC 기반 논리분리, Subnet 단위 격리, 운영/개발/DB 영역 간 VPC 분리), ② 접근통제(조번화 MFA, 외부 단말 차단, IP 기반 접근제어 — 시스템/DB 접근제어 솔루션 도입, 관리자 계정 간 IP 제어·MFA 적용), ③ 인증관리(역할기반 접근권한, DB 암호화 솔루션·암호화 키 분리관리 서버), ④ 데이터보호(암호화/비식별화/마스킹/키 분리관리/백업 암호화), ⑤ 통신경로(내부망 HTTPS 암호화, API Gateway 통한 요청제어, 관리자 접속 시 VPN 통한 암호화 접근), ⑥ 로그/감사(계정변경 자동감사, 이상행위 탐지, **접근기록 2년 이상 장기보관** — CSP 및 솔루션 제공 감사로그), ⑦ 운영환경(개발/운영 분리, 테스트망 접근통제, VPC 간 통신 내용 없음). (원본 p.535)
  - ⚠ **미반영 추정**: MFA는 admin 콘솔에 이미 부분 구현됨(`sfr_gap_fill_round2_mfa_destruction_sla` 메모 참고, "선택적"). DB 암호화/키 분리관리 서버, 2년 이상 로그 장기보관, VPC 망분리는 로컬 개발 단계에서 미구현 — 실이관 전 반드시 반영 필요한 항목으로 기록해 둘 가치 있음.

### Ⅲ.7 IT 거버넌스 수립 (p.541–589)

## 종합: 우리 구현과의 정합성 요약

전반적으로 우리가 이미 구현한 6-서비스 MSA(member/donation/point/gift/order/admin) 분할은 ISP 문서의 이벤트스토밍·바운디드컨텍스트·기능분해 3중 검증을 거친 6개 마이크로서비스(회원/기부/포인트/답례품/주문/운영) 설계와 **도메인 경계가 정확히 일치**한다. DB 분리 방식(공유 DBMS + 스키마 분리)도 ISP 설계와 부합. API Gateway로 Kong을 쓴 것도 ISP가 검토한 후보와 일치.

ISP 문서에 있지만 이 프로젝트에서 아직 반영되지 않은 것으로 보이는 항목(실제 클라우드 이관 단계의 과제이므로 당연한 것들 위주):
1. CDN(답례품 이미지 정적 콘텐츠) 서비스
2. Keycloak 등 중앙 IAM/계정 통합관리
3. 실제 VPC 망분리, WAF/IPS/IPSec VPN 등 네트워크 보안계층
4. N2SF 기준 DB 암호화·암호화 키 분리관리 서버, 2년 이상 감사로그 장기보관
5. CI/CD 파이프라인 자동화(ArgoCD/GitLab/Jenkins) 및 SAST/DAST 통합 DevSecOps
6. 상용 SW 연동(Fasoo DRM 문서보안, WEDDS BlackBox 개인정보접속기록, 제니퍼 APM, MagicLine PKI인증) — 현재 목업(enabled=false) 처리 상태와 부합
7. 정산(Settlement) 취소의 명시적 SAGA 보상 트랜잭션 여부 재점검
8. "알림게이트웨이"라는 별도 인터페이스 개념(현재는 서비스별 이메일 발송 등으로 처리 중으로 보임)

이 프로젝트가 "전환사업"(AS-IS 기능을 MSA로 이행)이라는 성격상 1~5는 실제 클라우드 배포 단계의 과제이며 소스코드/기능 구현 단계에서는 스킵이 합리적이다. 6~8은 기능 설계 차원에서 재검토 가치가 있다.
