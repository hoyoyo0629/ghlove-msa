# 서비스별 개발 난이도·공수 순위 (업무분장 회의용)

작성일: 2026-09-03 (2차 수정: 진척현황 제외한 그린필드 기준으로 재산정)
근거자료: `docs/as-is-feature-audit-{member,donation,point,gift,order,admin}.md` (6개 서비스 AS-IS 기능인벤토리 감사) +
실제 코드베이스의 Kafka 이벤트/SAGA 아키텍처 직접 확인 (`@KafkaListener` 16개 파일 전수조사)

> **전제**: "지금까지 개발된 진척현황(구현 완료 여부)"은 완전히 배제하고, **6개 서비스를 전부 처음부터 새로 만든다면** 어느 서비스가 본질적으로 더 어렵고 공수가 많이 드는가를 기준으로 산정. 그래서 아래 지표는 "남은 작업량(갭)"이 아니라 "전체 규모"와 "도메인/아키텍처 본질 복잡도"만 사용함.

## 0. 1차 순위표에서 수정된 부분 (중요)

1차 작성 때 admin의 "아키텍처 복잡도" 점수를 AS-IS 감사문서에 "Kafka/이벤트/SAGA"라는 **단어가 언급됐는지**로만 grep해서 매겼는데, 이건 틀린 방법이었음 — AS-IS 감사문서는 레거시 기능 매핑 문서라 TO-BE의 실제 Kafka 아키텍처는 애초에 거기 안 적혀 있음. 실제 코드(`@KafkaListener` 전수조사)를 확인한 결과:

- **admin에도 Kafka 리스너가 5개** 있음(`OrderStatsListener`/`GiftStatsListener`/`PointStatsListener`/`DonationStatsListener`/`OpenApiUsageListener`). 다만 코드를 열어보면 전부 `order.saga` 등 토픽을 구독만 하고 **"never publishes anything back"**(주석 원문) — 보상 트랜잭션 없는 순수 읽기전용 CQRS 리드모델 갱신용. 즉 "SAGA 참여자"는 아니지만 "이벤트 처리 복잡도 0"도 아님.
- 반대로 **실제 SAGA 보상 트랜잭션(Publisher+Listener 양방향)을 구현한 서비스는 order·gift·point 3개**임. `point/OrderSagaListener.java`를 직접 열어 확인: `ORDER_CREATED` 수신 시 포인트 차감 시도 → 실패하면 `publishPointDeductFailed` 발행, `ORDER_CANCELLED` 수신 시 포인트 복원까지 point 서비스가 직접 구현. gift도 동일 구조로 재고 예약/해제를 처리. 즉 **SAGA는 order 혼자가 아니라 order-gift-point 삼각 구조**이고, 원래 순위표는 이걸 order에만 몰아서 gift·point의 아키텍처 난이도를 과소평가했음.

이 두 가지를 반영해 아래 점수표를 재산정함.

## 1. 종합 순위 (그린필드 기준, 진척현황 무관)

| 순위 | 서비스 | 종합점수 (5개 기준 합산, 만점25) | 한줄 요약 |
|---|---|---|---|
| 1 | **order** (주문/장바구니/결제) | 22 | SAGA 삼각구조의 시작점(체크아웃 트리거+오케스트레이션 성격의 이벤트 발행). 쿠폰·지자체별 포인트 lot 카트 로직까지 겹침 |
| 2 | **donation** (기부) | 19 | 이 프로젝트의 핵심 도메인. 암호화(직인 AES-256-GCM), 외부연계 6종, 영수증 2종류, 세액공제 계산 등 도메인 규칙 밀도가 6개 중 최고 |
| 3 | **gift** (답례품몰) | 18 | **SAGA 보상 트랜잭션(재고 예약/해제) 직접 구현** + 상품 옵션·리뷰·Q&A·찜 등 카탈로그 도메인 자체도 넓음 |
| 4 | **admin** (관리자 콘솔) | 17 | 화면수 78개(실제 라우트 123개)로 전체 규모는 압도적 1위, RBAC 6단계. 다만 SAGA 보상 로직은 없고 Kafka도 읽기전용 CQRS라 아키텍처 본질 난이도는 중간 |
| 5 | **point** (포인트) | 16 | 기능 개수는 가장 적지만(19개) **SAGA 보상 트랜잭션(포인트 차감/복원) 직접 구현** + 지자체별 원장 필터링이라 "범위는 좁지만 밀도는 높음" |
| 6 | **member** (회원/인증) | 16 | 전 서비스 인증 기반이라 보안 민감도는 최고지만, JWT/RBAC/MFA는 업계 검증된 패턴이라 order·donation·gift보다 개념적 난이도는 낮음 |

> 4~6위(admin/point/member)는 사실상 동률(16~17)이며 **성격이 서로 다른 어려움**이라 우열보다 구분이 중요함 (3절 참고). SAGA 삼각구조(order·gift·point)는 서로 강하게 얽혀있어 팀을 완전히 분리해서 배정하면 통합 시점에 충돌 위험이 큼 — 4절 참고.

## 2. 판단 기준 (5개 지표, 각 1~5점)

진척현황(무엇이 끝났는지)에 의존하는 지표는 배제하고, **처음부터 만든다고 해도 변하지 않는 본질적 특성**만 사용함.

| 지표 | 의미 | 왜 중요한가 |
|---|---|---|
| **① 규모** | AS-IS 기능인벤토리 감사에서 확인된 전체 기능/화면 개수(완료 여부 무관) | 단순 작업량(공수) 대리지표 |
| **② 아키텍처 복잡도** | 분산 트랜잭션(SAGA 보상로직 실구현 여부)·이벤트 처리·암호화·다단계 상태머신 여부 - **실제 코드의 `@KafkaListener`/`Publisher` 전수조사로 재확인** | 버그 발생 확률과 디버깅 난이도를 좌우 |
| **③ 크로스서비스 의존도** | 다른 서비스 API/이벤트에 얼마나 걸쳐있는가 | 통합테스트·장애전파범위·팀간 조율 비용 |
| **④ 정합성/보안 민감도** | 금전(포인트·기부금)·개인정보·인증처럼 실수 시 파급효과가 큰 영역인가 | 리뷰·테스트를 더 꼼꼼히 해야 하는 영역 |
| **⑤ 도메인 규칙 밀도** | 단순 CRUD를 넘어서는 고유 비즈니스 규칙(세법·암호화·상태머신·권한체계)의 양 - AS-IS 감사에서 확인된 미구현 갭 건수는 "이 서비스가 원래 얼마나 규칙이 많은 영역인지"의 참고자료로만 사용(=처음부터 만들어도 똑같이 마주칠 규칙들) | 규칙이 많을수록 설계·리뷰에 드는 사고비용이 큼 |

## 3. 서비스별 상세 근거

### 🥇 order — 종합 난이도 1위
- SAGA 삼각구조(order-gift-point)의 **트리거이자 이벤트 오케스트레이션 시작점** (`order.saga` 토픽에 `ORDER_CREATED`/`ORDER_CANCELLED` 등을 발행하면 gift·point가 각자 보상처리). 처음부터 설계한다면 이 이벤트 스키마와 순서 보장을 order 쪽에서 가장 먼저 정의해야 함
- 장바구니가 **지자체별 포인트 lot 필터링**(전역 포인트가 아니라 `PT_POINT_LEDGER`를 지자체 단위로 관리)이라는 별도 도메인 규칙을 갖고 있고, 체크아웃이 N개의 단건 주문으로 팬아웃되는 구조라 트랜잭션 경계 설계가 까다로움
- **실제로 미인증 보안결함**이 발견됨: `/claims`, `/claims/{id}/approve,reject,complete` 등 클레임 처리큐가 인증 없이 인터넷에 노출되어 URL만 알면 누구나 임의 주문을 승인/거절할 수 있는 상태였음(`as-is-feature-audit-order.md`) — 새로 만들어도 놓치기 쉬운 유형의 실수라는 방증
- 쿠폰 서브시스템(신규 도메인)까지 order 내부에 있어 할인계산·포인트차감이 동시에 얽힘

### 🥈 donation — 도메인 규칙 밀도 최고
- 이 프로젝트의 본질 기능(기부)이 몰려있는 서비스. 지정기부/오프라인기부/세액공제/정책약관/직인암호화/영수증(확인증+단건공식영수증 2종) 등 하위 기능 다양성이 가장 큼
- **AES-256-GCM 암호화**(직인), 세액공제 계산 로직처럼 일반 CRUD로 안 끝나는 순수 도메인/보안 로직이 포함됨. SAGA에는 참여하지 않지만(이벤트는 발행만 함) 법·세무 규칙이 가장 촘촘함
- 외부연계(mock) 6종으로 6개 서비스 중 최다 - `LocalTaxClient` 등 실제 세외수입 연계 흐름까지 고려해야 함
- SmartEditor2/OZReport처럼 **상용 라이선스 제약**으로 설계 판단이 갈리는 영역이 있어 의사결정 비용도 있음

### 🥉 gift — SAGA 보상 트랜잭션 직접 구현 + 미구현 갭 최다(16건)
- `OrderSagaPublisher`/`OrderSagaListener`를 order와 동일하게 갖고 있는 **진짜 SAGA 참여자** - `ORDER_CREATED` 수신 시 재고 예약, `ORDER_CANCELLED` 수신 시 재고 해제(보상)를 gift가 직접 처리. 1차 순위표에서는 이 부분이 빠져서 과소평가돼 있었음
- AS-IS 감사에서 확인된 미구현 항목도 6개 서비스 중 가장 많음(16건) - 특히 **상품 옵션 시스템**, **배송비 계산 로직**은 처음부터 새로 설계해야 하는 영역
- 답례품 카탈로그(목록/상세/리뷰/Q&A/찜) 자체는 패턴화되어 있지만, 옵션/배송비 로직은 order·point의 SAGA 이벤트 페이로드에도 영향을 줄 수 있어 셋을 따로 떼어 설계하기 어려움

### admin — 전체 규모(공수) 기준 압도적 1위, 단 SAGA 참여는 없음
- AS-IS 기능인벤토리상 78개, 실제 구현된 라우트는 **123개**로 6개 서비스 중 압도적 최다 (`admin_console_real_asis_markup_round`, `admin_console_asis_design_round` 메모리 참고)
- RBAC이 **6단계**(ROLE_ADMIN_1~6 + 지자체담당자 데이터스코프)로 가장 세분화되어 있어 화면마다 권한체크가 다름
- **Kafka 리스너가 5개**(`OrderStatsListener`/`GiftStatsListener`/`PointStatsListener`/`DonationStatsListener`/`OpenApiUsageListener`) 있지만 전부 각 서비스 이벤트를 구독해 통계 ReadModel을 갱신하는 **읽기전용 CQRS**이고, 코드 주석에도 명시된 것처럼 "보상 트랜잭션을 발행하지 않음" — SAGA 참여자는 아님
- 개별 화면 자체는 대부분 CRUD/조회 패턴이 반복되는 구조라 **다수 인원이 화면 단위로 나눠 병렬 작업하기에 가장 적합한 서비스**

### point — 기능 범위는 최소지만 SAGA 보상 트랜잭션 직접 구현
- 기능 개수는 19개로 6개 서비스 중 최소지만, `OrderSagaListener.java`를 실제로 열어보면 `ORDER_CREATED` 수신 시 포인트 차감을 시도하고 실패하면 `publishPointDeductFailed`를 발행, `ORDER_CANCELLED` 수신 시 포인트를 복원하는 **완전한 SAGA 보상 로직**을 갖고 있음 - "범위는 좁지만 밀도는 높은" 유형
- 지자체별 원장 필터링(글로벌 포인트가 아님)까지 겹쳐서, 기능수만 보고 쉬운 서비스로 오판하면 안 됨

### member — 보안 민감도 최고, 개념 난이도는 상대적으로 낮음
- 전 서비스 인증의 기반이라 **정합성/보안 민감도는 최상위**(5점) - 여기서 나는 버그는 전 서비스로 전파됨
- Kafka 이벤트 참여가 전혀 없는 유일한 서비스. JWT/RBAC/휴면회원/MFA는 업계에 검증된 패턴이 이미 있어서, order의 SAGA나 donation의 암호화보다는 "어떻게 만들지 몰라서" 어려운 영역은 아님 - "실수하면 안 되기 때문에" 어려운 영역
- 실제로 ID/PW찾기, 역할신청/승인 등에서 JWT 쿠키 누락 같은 실버그가 발견된 이력 있음

## 4. 업무분장 시 참고 포인트

- **order·gift·point는 SAGA로 강하게 결합**되어 있음(`order.saga` 토픽 하나를 셋이 공유). 이 세 서비스를 서로 다른 팀에 완전히 분리 배정하면 이벤트 스키마 변경 시 3팀 동시 조율이 필요해짐 - 최소한 이벤트 계약(payload 구조) 설계만큼은 한 사람/한 팀이 먼저 정하고 시작하는 걸 권장
- **admin**은 반대로 다른 5개 서비스와 이벤트를 주고받긴 하지만 읽기전용이라 결합도가 낮음 - 인원을 가장 많이 투입해 화면 단위 병렬 처리가 가능하고, 신규 투입 인력 온보딩에도 적합
- **donation**은 도메인 지식(기부금 법률/세액공제/OZReport 라이선스 제약)이 필요해 프로젝트 히스토리를 아는 사람이 붙는 게 효율적
- **member**는 Kafka 이벤트 결합이 전혀 없어 상대적으로 독립적으로 배정 가능하지만, 보안 영향범위가 크므로 리뷰는 꼼꼼히
