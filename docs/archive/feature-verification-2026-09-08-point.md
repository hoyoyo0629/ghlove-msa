## 1. 🔴 심각 결함

### 1-1. 법정 상한(30%)을 넘는 포인트가 실제로 적립된다

적립률 상한 검증이 **저장(write) 경로에만** 있고, **적립(read/credit) 경로에는 클램프가 없다.**

```java
// 저장 시: 가드 있음 (게다가 상한값을 공통코드로 관리 - 하드코딩 금지 원칙 준수, 좋은 설계)
upsertLocgovPointRate() -> pointRate > maxPointRate() 이면 거부

// 적립 시: 클램프 없음 - DB 값을 그대로 사용
pointRateOf(year, locgovCode) -> DB 값 그대로 반환
```

문제는 **가드가 도입되기 전에 저장된 데이터가 이미 상한을 넘겨 남아 있다는 것**이다.

```
point.pt_locgov_point_rate (현재 데이터)
  11110 (서울 종로구)  40.00   ← 법정 상한 초과
  36110 (세종특별자치시) 35.00  ← 법정 상한 초과
  46150               25.00
  11230/26350/50000   30.00
```

실호출 검증 — 종로구에 10만원 기부:

```
POST /api/donate {"locgovCode":"11110","amount":100000}  -> 완료
GET  /api/balance?userId=1041 -> {"balance":40000}       ← 30,000이어야 함
원장 reason: "기부포인트 적립 (40.00%)"
```

고향사랑기부금법상 답례품 제공한도(기부금액의 30%)를 초과한다. 코드 주석 스스로가 이 한도를
근거로 저장 가드를 넣었다고 밝히고 있으므로, 읽기 경로에 클램프가 빠진 것은 명백한 누락이다.

**조치**: `pointRateOf()` 결과에 `min(rate, maxPointRate())` 클램프 적용 + 기존 초과 데이터(35%, 40%) 정비.

### 1-2. 기부 취소 회수 시 잔액 검사가 없어 **잔액이 음수가 된다**

`PointService.reverseForDonation()`은 중복 처리 방지(멱등성) 가드는 잘 갖췄지만,
**회수할 포인트가 이미 사용됐는지 확인하지 않고 원래 적립액 전액을 그대로 차감**한다.

```java
long reverseAmount = -original.getPointAmount();   // 적립 원금 전액
...
consumeLots(event.userId(), original.getPointAmount());
adjustBalance(event.userId(), reverseAmount);       // ← 가용 잔액 검사 없음
```

donation 검증에서 실증한 재현 경로:

```
포인트 잔액 11,970,000점 -> 11,900,000점 사용 (잔액 70,000점)
-> 해당 기부 취소 -> 잔액 -5,900,000점
```

대조적으로 **사용(use) 경로에는 가드가 정상적으로 존재**한다.

```
잔액 30,000에서 50,000 사용 시도 -> "보유 포인트가 부족합니다. (잔액: 30000P)"
음수 금액 사용 시도             -> "사용 포인트는 0보다 커야 합니다."
```

즉 방어선이 한쪽 경로에만 있다. ISP는 포인트를 "**화폐성 자원**으로 간주해 거래 무결성과 감사
추적 가능성을 확보"하라고 명시한다(원본 p.367). 음수 잔액은 이후 정산·통계 금액을 전부 오염시킨다.

**조치**: 회수 경로에도 가용 잔액 검사를 추가하고, 부족분은 (a) 취소를 거부하거나 (b) 별도의
"미회수 채권" 상태로 기록하는 정책을 세워야 한다. 최소한 `pt_point_balance.balance >= 0` DB 제약을 건다.

### 1-3. 관리자·내부 API 무인증 — **적립률을 인증 없이 변경할 수 있다**

member/donation과 동일한 패턴이다. point의 소스 주석은 이를 의도로 기술하고 있다.

> "동일하게 별도 인증 없이 열려있다(브라우저에 직접 노출되지 않고 admin 콘솔에서만 호출)"

그러나 서비스 포트(8083)에 도달만 하면 누구나 호출할 수 있으므로 이 전제는 성립하지 않는다.
인증 없이 성공한 호출:

```
GET  /api/admin/ledger/all              -> 전체 회원 포인트 원장 전량
GET  /api/admin/point-history           -> 포인트 거래 이력 전량
GET  /api/admin/point-daily-stats       -> 일별 적립/사용/소멸 통계
GET  /api/balance?userId=1000           -> {"balance":749900}  임의 회원 잔액
GET  /api/locgov-point-summary?userId=1000 -> 임의 회원의 지자체별 포인트 현황

POST /api/admin/locgov-point-rate
     {"stdrYear":"2026","locgovCode":"44770","pointRate":28,"managerName":"anon"}
  -> 200 저장 성공. 담당자명도 요청 본문 값 그대로 기록됨
```

**적립률은 기부금 대비 지급 포인트를 결정하는 재정 직결 설정값**이다. 이를 인증 없이 바꿀 수 있고,
변경 이력의 담당자명(`lastUpdusrNm`)마저 클라이언트가 지정하므로 감사 추적도 무의미해진다.

*완화 요소*: 상한(30%) 가드는 무인증 호출에도 정상 적용되어 50% 저장 시도는 거부됐다.

## 2. 🟠 중간 결함

### 2-1. 포인트 예약(reservation)이 실제 주문 흐름과 연동되지 않음

SFR-004는 포인트 관리 기능으로 "적립, 차감(주문결제), **예약/예약해제**, 소멸 처리"를 요구하고,
ISP 바운디드 컨텍스트 #3도 명령을 "포인트적립, **예약/사용, 예약해제**, 환불, 소멸"로 정의한다.

예약 기능 자체는 잘 구현되어 있고 정상 동작한다(§3 참조). 문제는 **실제 주문 결제가 이 예약 단계를
거치지 않는다**는 점이다. order SAGA는 `ORDER_CREATED` 이벤트에서 곧바로 `deductForOrder()`로 차감한다.

소스 주석도 이를 명시적으로 인정하고 있다.

```
// 포인트 예약 큐 (SFR-004 예약/예약해제) - 실제 order SAGA는 아직 이 API를 타지 않고
// 직접 차감/복원 방식을 그대로 쓴다 (틀만 먼저 마련해 두는 단계).

// (storefront PointReservationsView.vue)
// 실제 주문 결제는 아직 이 예약 단계를 거치지 않고 바로 차감/복원되므로(order SAGA 미연동),
// 독립적인 테스트/관리 용도로 쓰인다.
```

즉 마이페이지의 "포인트 예약" 화면은 **실제 업무와 무관한 독립 테스트 화면**이다.
예약 없이 즉시 차감하는 현재 방식은 주문 생성이 후속 단계에서 실패할 경우 보상 이벤트에
전적으로 의존하게 되어, 예약 방식보다 정합성 위험이 크다.

### 2-2. `ORDER_CONFIRMED` 이벤트를 구독하지 않음

order 서비스는 `ORDER_CREATED` / `ORDER_CANCELLED` / `ORDER_CONFIRMED` / `ORDER_CLAIM_UPDATED` /
`ORDER_DELIVERY_UPDATED`를 발행하는데, point의 `OrderSagaListener`는 앞의 두 개만 처리하고
나머지는 `default -> { /* not relevant */ }`로 흘려보낸다.

SFR-004는 "주문클레임 서비스 이벤트(**주문확정**/주문취소/반품완료 등)를 구독하여 원장 자동 갱신"을
요구한다. 예약 방식으로 전환하면 `ORDER_CONFIRMED`가 "예약 → 확정(사용)" 전환점이 되므로,
§2-1과 함께 묶어서 설계해야 한다.

*참고 — 이건 문제가 아니다*: **반품완료 시 포인트 복원은 정상 동작한다.** `ClaimService`가 반품
처리 완료 시 `publishCancelled(order)`로 `ORDER_CANCELLED`를 발행하고 point가 이를 구독해
`restoreForOrder()`를 수행하는 구조다. 별도 반품 이벤트가 없다고 해서 누락된 것이 아니다.

### 2-3. 상한 초과 적립률 데이터 잔존

§1-1의 데이터 측면. `11110`(40%), `36110`(35%)이 남아 있어, 클램프를 넣더라도 별도 데이터 정비가 필요하다.
관리 화면에서 다시 저장하기 전까지는 이 값들이 계속 노출된다.

## 5. 3개 서비스 종합 (member / donation / point)

### 공통 결함 — 세 서비스 전부에 해당

**모든 `/api/admin/**` 및 내부 연동 API가 무인증이다.** order에는 `AdminApiAuthInterceptor`가 있는데
member·donation·point에는 없다. 이 한 가지 누락으로 다음이 전부 열린다.

| 서비스 | 무인증으로 가능한 것 |
|---|---|
| member | 회원 PII 검색, 강제탈퇴, 권한 회수, 개인정보 파기 배치, 감사로그 전량, 임의 계정 생성 |
| donation | 기부 전체 원장, 세외수입 부과·수납 내역, 지자체 관리, 기탁서(개인정보), 승인자 ID 위조 |
| point | 전체 포인트 원장, 임의 회원 잔액, **적립률 변경**(담당자명까지 위조) |

ISP의 N2SF 보안설계상 회원정보·결제정보·관리자계정정보는 전부 **S등급(민감)** 이다.
**이것이 1순위 조치 항목이다** — 수정 비용은 작고(인터셉터 3개 추가) 노출 범위는 가장 넓다.

### 법정 요건 위반 3건

| 항목 | 서비스 | 내용 |
|---|---|---|
| 주민등록지 기부 금지 | donation | 거주지 오판으로 본인 주소지 기부 성공 |
| 연간 기부한도 | donation | 2,000만원 한도에 5,980만원 완료 |
| 답례품 제공한도 30% | point | 40% 적립 실제 발생 |

### 기능 불능 3건

| 항목 | 서비스 | 원인 |
|---|---|---|
| 배송지·회원등급 삭제 | member | `request_method varchar(5)` < "DELETE" |
| 기부금 운용현황 조회 | donation | `expndtr_de varchar(8)` ↔ `LocalDateTime` |
| 포인트 예약 → 주문 연동 | point | order SAGA 미연동 (기능은 있으나 실사용 경로 없음) |

### 잘 되어 있는 것 — 과소평가하면 안 되는 부분

- **기부 → Kafka → 포인트 적립 → 주문 차감 → 취소/반품 복원**으로 이어지는 이벤트 체인이 실제로 동작한다.
  SFR-008(이벤트 버스·SAGA)의 핵심은 구현되어 있다.
- **하드코딩 금지 원칙이 대체로 지켜진다** — 연간 한도, 지자체별 한도, 적립률, 적립률 상한,
  휴면 전환 기준일수가 모두 DB(공통코드/설정 테이블) 조회 방식이다. 예외는 기부 상태코드와
  세액공제 세율 2건이다.
- 계정 잠금·MFA·감사로그 3종·개인정보 파기 이력·포인트 FIFO/소멸/만료예정 등
  RFP가 요구한 세부 기능이 구조까지 갖춰 구현되어 있다.
