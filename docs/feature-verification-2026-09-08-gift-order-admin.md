# 기능 재검증 (2차) — 답례품(gift) / 주문(order) / 운영(admin) 서비스

검증일: 2026-09-08
기준 문서: `docs/requirements.md`(RFP SFR-005/006/007), `docs/isp-detailed-design-summary.md`(ISP 바운디드 컨텍스트 #4 주문, #5 답례품, #6 운영)
대상 커밋: `f567f7c 기능 상세 구현 1차`
선행 문서: member / donation / point 검증 문서 3종

member/donation/point과 동일하게 6개 서비스 전부 기동한 뒤, 앞 라운드에서 만든 회원·포인트를 이어받아
**기부 → 적립 → 장바구니 → 주문 → 배송 → 클레임 → 정산 통계**까지 실제 HTTP 호출로 관통 검증했다.

---

## 0. 결과 요약

| 서비스 | 🔴 심각 | 🟠 중간 | ✅ 정상 |
|---|---|---|---|
| gift (SFR-005) | 1 | 3 | 12 |
| order (SFR-006) | 1 | 2 | 11 |
| admin (SFR-007) | 0 | 3 | 14 |

**핵심 발견**
- **order와 admin은 유일하게 관리자 API 인증을 갖췄다.** order는 `AdminApiAuthInterceptor`(공유시크릿+관리자 신원 헤더), admin 콘솔은 비밀번호+이메일 MFA 2단계+계정잠금까지 정상 동작한다. member/donation/point의 무인증 문제(선행 문서 공통 결함)가 여기서는 반복되지 않는다.
- **gift는 member/donation/point와 같은 무인증 문제를 그대로 갖고 있다.** 관리자 상품/카테고리/승인/문의답변 API가 전부 무인증이다.
- **주문→포인트/재고 차감, 취소·반품→복원 SAGA가 실제로 완결 동작한다.** 실거래로 포인트 83,000·재고 1개 차감→복원까지 확인했다.
- **admin 통계 ReadModel이 전 도메인 Kafka 이벤트를 실시간·멱등 소비한다**(SFR-007/009 핵심).

# 답례품(gift) — SFR-005

## 1. 🔴 심각

### G-1. 관리자 API 전면 무인증 (member/donation/point와 동일 패턴)

gift에는 관리자 인증 인터셉터가 없다. 인증 없이 성공한 호출:

```
POST /api/admin/gift-items                     -> 상품 등록 성공 (즉시 APPROVED, §G-4)
POST /api/admin/gift-items/{id}/shipping       -> 배송정책 변경 성공
POST /api/admin/gift-items/{id}/approve|reject -> 승인/반려
GET  /api/admin/gift-items/pending             -> 승인대기 목록
GET  /api/admin/gift-categories/tree           -> 카테고리 트리 관리
POST /api/admin/gift-inquiries/{id}/answer     -> 고객 문의 답변 등록 성공
```

제공자/지자체 담당자만 접근해야 할 카탈로그·승인·문의답변이 무방비다. SFR-005의 "지자체 정책 관리:
답례품 승인/반려", "제공자별 등록/수정/중지/폐지" 권한 통제가 성립하지 않는다.

**조치**: order의 `AdminApiAuthInterceptor`를 gift에도 복제 적용.

## 2. 🟠 중간

### G-2. 답례품 승인/반려에 승인자·반려사유가 없다

```java
@PostMapping("/{id}/approve") public ResponseEntity<?> approve(@PathVariable Long id)   // 파라미터 id뿐
@PostMapping("/{id}/reject")  public ResponseEntity<?> reject(@PathVariable Long id)     // 반려사유 없음
```

누가 승인했는지, 왜 반려했는지 기록되지 않는다. 반려는 제공자에게 사유를 통지해야 하는 업무인데
사유 입력 자체가 없다. (상태 가드는 정상 — "승인 대기 상태인 답례품만 반려할 수 있습니다" 확인.)

### G-3. 관리자 직접 등록 시 승인 절차를 건너뛴다

`adminCreate()`는 주석 그대로 "관리자가 직접 만든 상품이라 승인 대기 없이 즉시 APPROVED+노출"이다.

```
POST /api/admin/gift-items (신규 등록) -> data_status_code=APPROVED, display_flag=Y 즉시
```

제공자 셀프 등록 경로(`register()`, PENDING 생성)는 코드에 존재하나 **현재 노출된 HTTP 진입점이 없다**
(`giftService.create()` 호출부 0건, SellerPortalController는 조회 전용). 즉 실제로 상품을 만드는 유일한
경로가 관리자 직접 등록이고, 그 경로는 지자체 승인 워크플로를 우회한다. SFR-005의 "승인/반려" 정책의
전제(제공자 신청 → 지자체 승인)가 실질적으로 작동하지 않는다.

### G-4. 행안부 표준 카테고리 체계 미적용

RFP SFR-005는 "행안부 표준 카테고리 체계 적용(매핑, 메타데이터 강화)"을 명시한다. 현재 카테고리는
자체 6종(TOUR/AGRI/SEAFOOD/PROCESSED/LIVING/VOUCHER)이며 행안부 표준 코드 매핑이 없다.
검색엔진(OpenSearch) 기반 통합검색·유사도 중복검사도 미도입(DB LIKE 검색). 이들은 실이관 단계
과제로 볼 여지가 있으나 RFP 명시 요건이므로 기록해 둔다.

# 주문(order) — SFR-006

## 1. 🔴 심각

### O-1. 고객이 자기 주문의 송장번호 등록·배송상태 변경을 직접 할 수 있다

배송 관련 엔드포인트가 `OrderMyApiController`(고객용)에 있고 **소유권·권한 검사가 없다.**

```java
@PostMapping("/api/orders/{orderId}/invoice")         // 소유권 검사 없음
@PostMapping("/api/orders/{orderId}/delivery-status")  // 소유권 검사 없음
```

실호출로 재현:

```
로그인 고객이 자기 주문에 대해:
POST /api/orders/{id}/invoice {"carrierCode":"CJ","invoiceNo":"123456789012"}  -> 등록됨
POST /api/orders/{id}/delivery-status {"deliveryStatus":"DELIVERED"}           -> 배송완료로 변경됨

심지어 쿠키(로그인) 없이도:
POST /api/orders/{fresh-order}/invoice          -> 204 (송장 등록 성공)
POST /api/orders/{fresh-order}/delivery-status  -> 204 (배송완료 처리 성공)
```

SFR-006은 "배송관리: 송장번호 등록, 배송상태 추적, 배송완료 처리"를 **판매자/운영 기능**으로 규정하고,
"택배사 시스템 연계는 운영관리 서비스가 담당(역할 분리)"이라고 명시한다. 그런데 구매자(또는 익명)가
자기 주문을 **배송완료로 스스로 처리**하면, 뒤이은 구매확정(수취확인) → 정산 확정으로 이어지는
흐름을 고객이 임의 앞당길 수 있다. 배송 상태 위조는 정산 신뢰성에 직결된다.

*대조*: 배송지 변경(`/delivery-address`)은 로그인+소유권 검사가 있어 무인증 시 401을 반환한다.
즉 같은 컨트롤러 안에서도 방어가 엇갈린다.

**조치**: invoice/delivery-status는 `AdminApiAuthInterceptor`가 걸린 `OrderAdminApiController`로 이관하거나,
최소한 판매자 신원 검증을 추가해야 한다.

## 2. 🟠 중간

### O-2. 배송완료 자동 구매확정·구매확정 기간 단축 미구현

RFP SFR-006은 "배송 자동화 및 구매확정 프로세스 개선(**배송완료 자동처리, 구매확정 기간 단축**)"을 요구한다.
현재 구매확정은 배송완료 상태에서 **구매자 본인이 수동으로**만 가능하고(`confirm-receipt`), 일정 기간
경과 시 자동 확정하는 배치가 없다(order의 `@Scheduled`는 쿠폰 배치뿐). 미확정 주문이 정산으로
넘어가지 못하고 적체될 수 있다.

### O-3. SLA ReadModel 미구현

RFP는 "통계 및 SLA 관리를 위한 ReadModel 제공(제공자·지자체별 SLA 지표)"을 요구한다. order에는
배송 이벤트(`OrderDeliveryUpdatedEvent`) 발행은 있으나 SLA 지표(배송 소요시간, 지연율 등)를 집계하는
ReadModel이 없다. admin 통계 ReadModel도 SLA 축은 다루지 않는다.

## 3. ✅ 정상 (order)

| # | 기능 | 결과 |
|---|---|---|
| 1 | 장바구니 담기/조회 | 지자체별 그룹핑, 보유포인트 표시, 라인합계 정상 |
| 2 | 결제 검토(review) | 그룹·총액·쿠폰옵션 정상 |
| 3 | **포인트 부족 사전 차단** | 잔액 60,000 < 주문 80,000 → "포인트가 부족합니다" (주문 생성 안 됨) |
| 4 | **주문 완료 → SAGA 차감** | 포인트 83,000(상품 80,000+배송 3,000) 차감, 재고 46→45 |
| 5 | 주문 상세 | 상태·배송·클레임 가능여부·택배사 목록 정상 |
| 6 | 수취확인(구매확정) | 배송완료 상태에서 본인만 가능(가드 확인) |
| 7 | 반품 신청 | 주문확정 상태 검사, 중복신청 방지 |
| 8 | **클레임 승인→완료 → 복원 SAGA** | 반품완료 시 포인트 83,000·재고 1개 **정확히 복원** |
| 9 | 주문 취소 → 복원 | 취소 시 포인트·재고 복원 확인 |
| 10 | 관리자 클레임 API 인증 | **무인증 401**, 공유시크릿+관리자헤더로만 접근(정상) |
| 11 | 쿠폰 조회 | 발급가능/보유 쿠폰 조회 정상 |

*SAGA 관련 특기사항*: 주문 생성은 `ORDER_CREATED` 발행 → point가 차감 후 `PointDeducted`/`PointDeductFailed`
발행 → gift가 재고 예약, 클레임/취소는 `ORDER_CANCELLED` 재사용으로 point·gift가 복원하는
Choreography SAGA가 실제로 완결 동작한다. 멱등성 가드(중복 이벤트 skip)도 gift/point 양쪽에 존재.

# 운영(admin) — SFR-007

admin은 6개 중 가장 크고(컨트롤러 91개), 인증 체계가 가장 견고하다. seed 관리자 비밀번호가 문서에
없어, 값을 아는 임시 BCrypt 해시를 admin01에 일시 적용해 로그인한 뒤 **원본 해시로 복원**하는 방식으로
콘솔 관리 화면까지 실제 검증했다(사용자 승인 하에 진행, 검증 후 원상복구 완료).

## 1. 🔴 심각
없음.

## 2. 🟠 중간

### A-1. 회원관리 기본 조회가 "오늘 가입자"만 표시 (member §3-2와 동일 뿌리)

관리자 콘솔 "회원관리" 목록의 조회 기간 기본값이 **오늘(가입일)** 이다.

```
/admin/members                                    -> 총 3건 (오늘 가입 3명만)
/admin/members?fromDate=2020-01-01&toDate=2027-12-31 -> 총 25건 (전체)
member API: /api/admin/members/search (기본)      -> totalElements 3
            + fromDate/toDate 지정                 -> totalElements 25
```

운영자가 날짜를 직접 넓히기 전에는 전체 회원의 12%만 보인다. member 서비스의 휴면회원 조회(§3-2)와
동일한 설계 문제이며, "회원 검색이 안 된다"는 민원으로 직결된다. 기본값을 "전체"로 바꿔야 한다.

### A-2. 회원 PII를 마스킹·재확인 없이 즉시 노출

관리자 회원 상세(`/admin/members/{userId}`)가 이름/이메일/연락처를 **마스킹 없이 평문**으로 렌더한다.
AS-IS 감사 문서(`as-is-feature-audit-member.md`)는 원 시스템이 "PII 마스킹+비밀번호 재확인 열람"이었다고
기록하는데, 현재는 열람 시 비밀번호 재확인 절차가 없다. ISP N2SF 보안설계상 회원정보는 S등급이므로
열람 통제(재인증)와 열람 이력 기록이 필요하다.

### A-3. 지자체 전용 대시보드 별도 앱 미분리 + SLA/구매확정 통계 공백

RFP SFR-007은 "지자체 전용 대시보드는 별도 애플리케이션으로 분리(경량화)"를 명시하나, 별도 앱은 없고
admin 콘솔 내 통계 화면으로 통합돼 있다(설계 스타일 차이로 볼 수 있음). 또한 order의 SLA 지표(O-3)가
없어 admin 대시보드에서도 배송 SLA를 볼 수 없다.

## 3. ✅ 정상 (admin)

| # | 기능 | 결과 |
|---|---|---|
| 1 | **콘솔 인증 게이트** | 비로그인 시 `/admin/login`으로 302 리다이렉트 |
| 2 | **로그인 MFA 2단계** | 비밀번호 확인 → 이메일 인증번호 → 세션 확정 (실제 통과 확인) |
| 3 | **계정 잠금** | 5회 실패 시 잠금, "이용할 수 없는 계정 (상태: 잠금)" (검증 중 실제 발생) |
| 4 | 관리자 액션 감사로그 | 로그인 성공/실패, 관리자 액션, 회원 변경 로그 4종 조회, admin01 로그인 기록 확인 |
| 5 | **통계 ReadModel(Kafka)** | 기부/주문/포인트/클레임 원장을 이벤트로 실시간 적재, 이번 세션 거래(13:17)까지 반영 |
| 6 | **ReadModel 멱등성** | `earliest` 재생 소비에도 cntr_sn 중복 0건(upsert) |
| 7 | 정산 4단계 상태머신 | 생성→세금계산서발행→입금확인→마감 순서 강제, 역행 차단 |
| 8 | 정산 취소 보상 | 주문 취소 이벤트 → `adjustForCancelledOrder`로 정산 조정 |

## 4. 6개 서비스 전체 종합

### 관리자 API 인증 현황 (선행 문서 공통 결함의 전체 그림)

| 서비스 | 관리자 API 인증 | 비고 |
|---|---|---|
| member | ❌ 없음 | PII·강제탈퇴·파기 노출 |
| donation | ❌ 없음 | 기부원장·세외수입·승인자위조 |
| point | ❌ 없음 | 적립률 무단 변경 |
| gift | ❌ 없음 | 카탈로그·승인·문의답변 |
| **order** | ✅ **인터셉터 보유** | 단, 배송 일부가 고객 API에 노출(O-1) |
| **admin** | ✅ **MFA+잠금+세션** | 콘솔 인증 견고 |

order의 `AdminApiAuthInterceptor`가 이미 검증된 레퍼런스 구현이므로, 이것을 member/donation/point/gift에
복제하는 것이 **가장 비용 대비 효과가 큰 1순위 조치**다(4개 서비스 × 인터셉터 1개).

### 실제로 잘 되는 것 — end-to-end 관통 확인

이번 검증에서 **기부 → 포인트 적립 → 장바구니 → 주문 → 포인트/재고 차감 → 배송 → 반품 → 포인트/재고
복원 → 정산 통계 적재**까지 6개 서비스를 가로지르는 전체 흐름이 실거래로 완결됨을 확인했다.
SFR-008(이벤트 버스·SAGA)·SFR-009(CQRS ReadModel)의 핵심 골격은 구현되어 동작한다.

### 반복되는 3대 패턴 (6개 서비스 공통 교훈)

1. **관리자 API 인증 누락** — order/admin 제외 4개 서비스.
2. **조회 기본값이 "오늘"** — member 휴면조회(§3-2), admin 회원조회(A-1). 운영자가 기간을 넓히기 전엔 빈 화면.
3. **검증이 신청/저장 시점에만, 확정/조회 시점 재검증 없음** — donation 한도(신청시만), point 적립률(저장시만),
   gift 승인(직접등록 우회). 상태 전이의 뒷단에 방어선이 비어 있다.

### 법정/금액 무결성 관련 (앞 문서 재확인)

order/gift/admin 검증에서는 새로운 법정 위반은 발견되지 않았다. 다만 O-1(고객의 배송완료 위조)은
정산 신뢰성에, G-3(승인 우회)은 지자체 통제에 각각 영향을 준다.
